# Step 3 - Real Telegram verification on Render (temporary, Android-friendly)

A temporary, web-only deployment on Render from the repository's `render.yaml`: one Free web service (the existing
Dockerfile) and one Free PostgreSQL database in the same region. It is only for the Step 3 check (Telegram account
connection, code, 2FA, disconnect). The 16-step table, PASS/FAIL rules and security checklist are in
[STEP3_REAL_TELEGRAM_VERIFICATION.md](STEP3_REAL_TELEGRAM_VERIFICATION.md).

> ## NEVER share secrets
> Do not send anybody (not the developer, not an AI assistant, not in a GitHub issue or chat) your Telegram login code,
> two-step password, API ID, API hash, session, the setup token, `APP_SECRET` or `SESSION_ENCRYPTION_KEY`. Report only
> PASS/FAIL and on-screen error texts. Never forward a login code in any Telegram chat. Do not commit secrets to GitHub.

**This has not been run on Render yet.** Everything below follows Render's documentation and automated tests of the
configuration, not a real deployment.

## What the Blueprint does
* `DATABASE_URL` comes from the Render Postgres *internal* connection string; the database accepts **no external connections**
  (`ipAllowList: []`).
* `APP_SECRET`, `SESSION_ENCRYPTION_KEY`, `SETUP_TOKEN` are generated by Render; nothing secret is in GitHub.
* `APP_URL` is not set: the app uses Render's `RENDER_EXTERNAL_URL` (`https://<name>.onrender.com`). Production-mode HTTPS
  validation is unchanged; an explicit `APP_URL` always wins.
* `APP_ENV=development` and `LICENSE_ENFORCEMENT=false`: the app allows disabled licensing only in development mode and there
  is no license server yet. Temporary test profile only. Cookies are still `Secure`/`HttpOnly`/`SameSite=Lax` (`__Host-` prefix).
* Migrations run automatically at start-up (`AUTO_MIGRATE=true`) under a PostgreSQL advisory lock with checksum checks.
* `PORT=8000` matches the Dockerfile. No worker is deployed (not needed for Step 3; Render Free has no free worker).

## Steps (Android browser)
1. **Commit and push** the new files (`render.yaml`, the config change) to GitHub; CI must stay green.
2. In the Render dashboard **delete the earlier failed web service** (and any database created for it) so names do not clash.
3. Render -> **New** -> **Blueprint** -> connect the GitHub repository `telegram-autopost-bot` -> Render reads `render.yaml`.
   Check that it lists one web service and one Postgres database (Free) and no other resource -> **Apply**.
   If Render reports that the Free plan or the region is unavailable, edit `plan` / `region` in `render.yaml` (both must use the same region) and push.
4. Wait for the first deploy (several minutes). The service URL is `https://telegram-auto-poster-test.onrender.com`
   (Render may add a suffix if the name is taken: use the URL Render shows).
5. Open `<service URL>/health/ready` -> `{"status":"ready"}`.
6. **Setup token:** Render dashboard -> the web service -> **Environment** -> `SETUP_TOKEN` -> reveal/copy it.
   Paste it only into the app's first-run page. After the administrator exists the setup page returns 404; you may then delete the variable.
7. Do **steps 1-16** of the main table on the service URL. Free-tier notes: a service that was idle for 15 minutes needs about a minute
   to wake on the next request; if a page times out, reload once. A login in progress is stored in the database, so a wake-up does not lose it
   (it expires after 10 minutes).
8. **Log checks:** Render dashboard -> web service -> **Logs**. Use the search box for the first 6 characters of your API hash,
   your login code, your 2FA password and your phone digits: expected **no results**. Page-source checks as in the main document
   (`view-source:<service URL>/telegram`, Find in page for hash prefix, phone digits, `gAAAA`: no matches).
9. Database-level checks of the main document need a database console; the database is private and Render Free offers no shell
   for this setup, so they are **not available** here. Say "not run" for them.

## Cleanup
1. In the app: **Disconnect**, then **Remove** the account; confirm **Telegram Auto Poster** is gone in Telegram -> Settings -> Devices.
2. Render dashboard -> the web service -> Settings -> **Delete Web Service**; then the database -> Settings -> **Delete Database**.
   Also delete the Blueprint entry if it remains. Confirm the dashboard lists no resources.
3. Free Postgres expires 30 days after creation anyway, but do not rely on that.

## Limits specific to Render Free (from Render's documentation)
* Free web services spin down after 15 minutes without inbound traffic and may be restarted at any time; the local file system is lost.
* Free Postgres expires 30 days after creation, has no backups and no managed connection pooling.
* Free instance hours are limited per month; plans, regions and free-tier availability can change.
* This is a data-centre IP: Telegram may show security notices or delay codes. Prefer a non-critical account.
* Behind Render's proxy all visitors appear with the proxy's address unless `TRUST_PROXY_HEADERS` is enabled. It is left off because
  Render's header behaviour was not verified; the login/code rate limits are therefore shared by all visitors. Fine for one tester.
