# Step 3 - Real Telegram verification on Render (temporary, Android-friendly)

A temporary, web-only deployment on Render from the repository's `render.yaml`: **one Free web service** (the existing
Dockerfile) that connects to the **PostgreSQL database `poster-test-db` you already created by hand** (Oregon).
It is only for the Step 3 check (Telegram account connection, code, 2FA, disconnect). The 16-step table, PASS/FAIL rules and
security checklist are in [STEP3_REAL_TELEGRAM_VERIFICATION.md](STEP3_REAL_TELEGRAM_VERIFICATION.md).

> ## NEVER share secrets
> Do not send anybody (not the developer, not an AI assistant, not in a GitHub issue or chat) your Telegram login code,
> two-step password, API ID, API hash, session, the setup token, `APP_SECRET`, `SESSION_ENCRYPTION_KEY` or the database URL.
> Report only PASS/FAIL and on-screen error texts. Never forward a login code in any Telegram chat. Do not commit secrets.

**This has not been run on Render yet.** Everything below follows Render's documentation and automated tests of the
configuration, not a real deployment.

## What the Blueprint does (and does not do)
* It declares **only the web service**. It does **not** declare any database, so it can neither create a duplicate nor try to change
  `poster-test-db` (PostgreSQL 18, Oregon; those settings cannot be changed after creation).
* `DATABASE_URL` uses `fromDatabase` -> `poster-test-db` -> `connectionString`: Render's **internal** connection string.
  According to Render's tutorials, `fromDatabase` finds a database "declared in the same Blueprint or already provisioned in the
  workspace"; I could not confirm this on a real workspace. `render blueprints validate` checks that the name exists.
* Web service region = `oregon`, equal to the database region (required for the internal hostname to work).
* `APP_SECRET`, `SESSION_ENCRYPTION_KEY`, `SETUP_TOKEN` are generated by Render; nothing secret is in GitHub.
* **Render-generated `SESSION_ENCRYPTION_KEY` is supported.** The application accepts either a ready-made Fernet key (used as is)
  or any other random secret of at least 32 characters (no spaces/commas), such as the value Render's *Generate* button or
  `generateValue` produces. The latter is converted to a Fernet key with HKDF-SHA256: deterministic, so the same value gives the same
  key at every start and deployment. The derived key is never stored or logged. **Do not change or regenerate the value** once an account is
  connected: sessions encrypted under it could no longer be read (you would simply connect the account again).
* `APP_URL` is not set: the app uses Render's `RENDER_EXTERNAL_URL` (`https://<name>.onrender.com`). Production-mode HTTPS
  validation is unchanged; an explicit `APP_URL` always wins.
* `APP_ENV=development` and `LICENSE_ENFORCEMENT=false`: the app allows disabled licensing only in development mode and there
  is no license server yet. Temporary test profile only. Cookies are still `Secure`/`HttpOnly`/`SameSite=Lax` (`__Host-` prefix).
* Migrations run automatically at start-up (`AUTO_MIGRATE=true`) under a PostgreSQL advisory lock with checksum checks.
* `PORT=8000` matches the Dockerfile. No worker is deployed (not needed for Step 3).
* **Not tested:** the application and its CI use PostgreSQL 16; `poster-test-db` is PostgreSQL 18. The SQL is standard, but this
  combination has never been run. A start-up error mentioning the database would be the first sign.

## Manual preconditions in the Render dashboard (the Blueprint cannot do these for a database it does not manage)
1. **Access Control of `poster-test-db`:** open the database -> *Info* / *Access Control* (wording may differ) and make sure
   **no external source** is allowed (remove `0.0.0.0/0`). The app uses only the private-network address.
2. **Clean up the failed Blueprint sync:** Dashboard -> *Blueprints*: delete the failed Blueprint entry, and delete any web service or
   database it created (for example a second database). Only `poster-test-db` should remain, plus nothing named
   `telegram-auto-poster-test` (otherwise Render will try to update that old service instead).
3. Confirm `poster-test-db` shows **Available** and Region **Oregon**.

## Steps (Android browser)
1. **Commit and push** the changed files to GitHub; CI must stay green.
2. Do the three manual preconditions above.
3. Render -> **New** -> **Blueprint** -> connect repository `telegram-autopost-bot` -> Render reads `render.yaml`.
   The summary must list **one web service and no database**. If it lists a database, **stop** and do not apply.
   If Render reports that `fromDatabase` / `poster-test-db` is unknown, see *If the Blueprint cannot find the database* below.
   -> **Apply**.
4. Wait for the first deploy (several minutes). Use the URL Render shows (normally `https://telegram-auto-poster-test.onrender.com`).
5. Open `<service URL>/health/ready` -> `{"status":"ready"}`.
6. **Setup token:** Render dashboard -> the web service -> **Environment** -> `SETUP_TOKEN` -> reveal/copy it. Paste it only into the
   app's first-run page. After the administrator exists the setup page returns 404; you may then delete the variable.
7. Do **steps 1-16** of the main table on the service URL. Free-tier note: after 15 minutes without traffic the service sleeps and
   needs about a minute to wake; reload once if a page times out. A login in progress is stored in the database, so a wake-up does not lose it
   (it expires after 10 minutes).
8. **Log checks:** Render dashboard -> web service -> **Logs**. Search for the first 6 characters of your API hash, your login code, your
   2FA password and your phone digits: expected **no results**. Page-source checks as in the main document
   (`view-source:<service URL>/telegram`, Find in page for hash prefix, phone digits, `gAAAA`: no matches).
9. Database-level checks of the main document need a database console and are **not available** here: report them as "not run".

### If the Blueprint cannot find the database
Do **not** declare a database in `render.yaml` as a workaround (that would try to create or modify one). Use Render's
supported manual setting instead: create the service from the Blueprint with the `DATABASE_URL` variable left empty (or let the
first deploy fail), then in the web service -> **Environment** set `DATABASE_URL` to the **Internal Database URL** shown on the
`poster-test-db` page (copy it there; it contains the password, so never paste it anywhere else), and **Manual Deploy**. Because
the Blueprint would overwrite a wired variable on the next sync, do not sync the Blueprint again afterwards. Tell the developer the
exact Render error text (no URLs or passwords) so the file can be fixed properly.

## Cleanup
1. In the app: **Disconnect**, then **Remove** the account; confirm **Telegram Auto Poster** is gone in Telegram -> Settings -> Devices.
2. Render dashboard -> the web service -> Settings -> **Delete Web Service**; then `poster-test-db` -> Settings -> **Delete Database**.
   Also delete the Blueprint entry if it remains. Confirm the dashboard lists no resources.
3. Free Postgres expires 30 days after creation anyway, but do not rely on that.

## Limits specific to Render Free (from Render's documentation)
* Free web services spin down after 15 minutes without inbound traffic and may be restarted at any time; the local file system is lost.
* Free Postgres expires 30 days after creation, has no backups and no managed connection pooling.
* Free instance hours are limited per month; plans, regions and free-tier availability can change.
* This is a data-centre IP: Telegram may show security notices or delay codes. Prefer a non-critical account.
* Behind Render's proxy all visitors appear with the proxy's address unless `TRUST_PROXY_HEADERS` is enabled. It is left off because
  Render's header behaviour was not verified; the login/code rate limits are therefore shared by all visitors. Fine for one tester.
